# Agent 学习与能力路线

## 北极星

通过构建一个**可观测、可评测、可复现实验**的最小 Agent Harness，理解 Agent 系统中模型、Harness、工具、上下文、权限和环境之间的边界。

不是以“支持多少工具”或“仿造 Claude Code 到什么程度”衡量进度，而是以以下问题是否有实验结果来衡量：

- 模型为什么选择这个工具？
- 工具 observation 是否提供了足够高信号？
- 上下文何时失真或耗尽？
- 工具失败后 Agent 能否恢复？
- 权限由 Prompt 约束还是由 Harness 强制执行？
- 换模型后成功率、步数和成本如何变化？

- `off`、`extractive`、`model` 三种压缩策略，默认 `off`
- 基于上一轮真实 `prompt_tokens` 触发，保留 system、最新 user 与最近窗口
- 工具名、路径、行号、错误、TODO、关键值和分页元数据的确定性证据提取
- 模型摘要无工具调用，异常、空输出、超限或缺证据时回退

M1.2 的机制与实验闭环已经完成，但结果**没有证明压缩提高成功率**：本轮 `off` 为 4/6，`extractive` 和 `model` 均为 3/6。压缩降低了本轮上下文和主模型 Token，同时暴露了证据时序、重复值和重复压缩失真。长目录策略仍待独立验证，因此不把当前结果外推为普适的上下文管理结论。下一阶段进入 M2 验证闭环。

## 非目标

当前阶段明确不做：

- Web UI
- 多 Agent 编排
- RAG / 向量数据库
- 大规模工具市场
- 自研 MCP 平台
- 生产级 Sandbox 宣传

这些能力只有在核心 Harness 和评测基线稳定后才值得引入。

## 阶段路线

### M0：Harness 正确性

学习问题：Agent 的运行契约是否可靠？

重点：

- Tool Schema 与消息协议
- 工具参数校验
- tool_call 与 tool message 一一配对
- 最大步数、超时和错误回传
- 配置与依赖可复现

验收：

- 所有工具 Schema 契约测试通过
- 10 个固定任务可重复运行
- 非法参数、未知工具和超时不会导致进程崩溃

### M1：上下文管理

学习问题：什么信息应该进入模型上下文，什么应该被压缩或丢弃？

重点：

- 分段读取和分页（M1.1 已完成）
- Token/字符预算（M1.1 已完成观测）
- 工具 observation 的信息密度（M1.1 已完成首轮对照）
- 历史消息压缩（M1.2 已完成机制与实验，默认 `off`；成功率收益未证明）
- 长文件和大目录策略（长文件分页已完成，目录策略待验证）

验收：

- [x] 长文件任务不因一次 observation 爆上下文
- [x] 记录每轮 tokens、字符数和步数
- [x] 对比“完整读取 / 分段读取 / 摘要压缩”的成功率与成本；本轮未发现压缩提高成功率
- [ ] 验证长目录组织与选择策略（不属于 M1.2 的完成声明）

M1.1 的实测与边界见 [M1_CONTEXT_BASELINE.md](M1_CONTEXT_BASELINE.md)，M1.2 的三策略结果、失败样本和限制见 [M1_2_COMPACTION_BASELINE.md](M1_2_COMPACTION_BASELINE.md)。

### M2：验证闭环

学习问题：Agent 如何知道自己真的完成了任务？

重点：

- 从整文件覆盖升级到 `apply_patch`
- 修改后自动执行测试、lint 或读取校验
- 根据验证错误继续修复
- 完成条件与停止条件

验收：

- 一组代码修改任务必须通过真实测试才算完成
- 记录首次修改成功率、验证轮次和修复成功率
- 模型声称完成但测试失败的情况应计入失败

### M3：失败恢复

学习问题：哪些错误应该重试，哪些错误必须停止？

重点：

- 模型 API 错误、工具参数错误、工具执行错误分类
- 只对幂等或明确暂态错误重试
- 避免写操作重复执行
- 超时、取消和最大成本预算

验收：

- 错误分类覆盖表
- 重试不会产生重复副作用
- 失败后恢复率有基线数据

### M4：安全边界

学习问题：如何把“Prompt 要求”变成“Harness 保证”？

重点：

- 工具能力分级
- 审批策略与最小权限
- 容器或进程级隔离
- 网络、文件、环境变量权限
- 对抗用例测试

验收：

- 路径逃逸、符号链接逃逸和越权访问被运行时阻断
- 写与执行操作必须有明确策略
- 隔离环境中的恶意代码不能访问宿主敏感资源

### M5：MCP 与 Skill

学习问题：什么时候应该使用进程内工具、MCP 或 Skill？

重点：

- 同一能力分别用原生 Tool 和 MCP 实现
- 比较耦合度、生命周期、错误语义、部署成本
- Skill 作为可复用的流程封装

验收：

- 同一任务的两种实现可对照评测
- 能说明 MCP 解决了什么问题，以及引入了什么成本

### M6：行业应用

学习问题：通用 Agent Harness 如何迁移到游戏日志/玩家舆情分析？

重点：

- 数据集与领域评测
- 证据引用与结论可追溯
- 分析结果的结构化输出
- 与 Game Analyzer / Game Lab 的分析→生成闭环结合

验收：

- 有领域数据、标准答案或人工标注基线
- 报告准确率、证据覆盖率和不支持结论率
- 不只是“看起来像分析”的 Demo

## 每一轮迭代的固定方法

采用 [Spec-Driven Development](SDD.md)，并遵守 [项目 Constitution](CONSTITUTION.md)：

1. Spec：写问题、假设、范围、非目标、需求 ID 和验收标准。
2. Plan：说明方案、文件影响、测试、安全边界、回滚和 ADR 需求。
3. Tasks：拆成带依赖和完成证据的任务。
4. Implement：实现最小变更并保留 Trace / 评测结果。
5. Verify：运行确定性测试、静态检查和固定评测。
6. Record：在 `implement.md` 记录实际结果、偏差、失败和已知限制。
7. Baseline：将可复用的指标沉淀到基线，不覆盖失败历史。

每个阶段使用独立文件：

```text
docs/specs/<milestone>-<slug>/
  spec.md
  plan.md
  tasks.md
  implement.md
```

可从 [模板目录](templates/) 复制。不要用“功能已增加”作为完成标准，用**可重复的行为变化**作为完成标准。
