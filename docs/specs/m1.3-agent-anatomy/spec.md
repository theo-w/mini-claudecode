## 1. 背景与问题

M1.1 和 M1.2 已产生 Token、上下文、压缩、工具调用和逐检查项数据，但这些数据主要以 JSON 和 Markdown 存在。学习者可以知道一次实验通过 3/6，却不容易回答：

- 当前 Agent 由哪些模块组成，各模块源码在哪里？
- 工具如何注册、模型如何发起调用、审批和 observation 在哪里发生？
- 某一轮 Loop 中，模型、工具、上下文与压缩按什么顺序运行？
- 两组参数从哪一个任务、哪一个检查项和哪一个事件开始出现差异？

现有 `ToolRegistry` 已持有真实工具 Schema，`EventTracer` 已持有真实事件。缺少的是这些事实的只读投影，而不是另一套模拟 Agent。

## 2. 目标

交付一个无需前端构建、仅在本地运行的 Agent 拆解台：

1. 用卡片展示真实模块、七个内置工具、源码位置、调用契约与风险；
2. 从现有 Eval JSON 导出一个本地 Dashboard 数据文件；
3. 用真实 Trace 回放 Loop，支持逐事件查看模型输出、工具参数、observation、压缩与停止原因；
4. 并排比较两份实验的配置、指标、任务 checks 和运行路径；
5. 新 Trace 使用 `call_id` 关联工具调用，旧报告仍可回放；
6. 明确区分代码测试、单次 Live Eval 快照和 UI 展示，不制造新的成功率结论。

## 3. 用户故事或实验场景

- 作为学习者，我希望点击 `read_file` 卡片后看到用途、源码、JSON 参数、审批风险和本次实验中的真实调用。
- 作为学习者，我希望逐步播放一次任务，观察 `model_response → tool_call → tool_result → 下一轮` 的真实内容与上下文变化。
- 作为实验者，我希望选择 `off` 与 `extractive`，看到参数差异、Token/成功率/耗时以及每个任务 checks，而不只看到一个总分。
- 给定旧版 M1.2 报告，当其中没有 `call_id` 时，导出器仍按 step、工具名和参数建立最佳努力关联，并标明这是兼容推断。
- 给定没有生成数据文件的干净 checkout，页面应显示导出命令，而不是伪造演示运行。

## 4. 范围

- 新增真实模块与工具目录生成器；
- 新增多报告 Dashboard JSON 导出命令；
- 新增静态 HTML/CSS/JavaScript 三视图：架构拆解、Loop 回放、实验对比；
- 新增工具事件 `call_id` 和旧报告兼容关联；
- 增加确定性测试、真实报告导出验证和浏览器交互验证；
- 更新 README、Roadmap、规格索引、ADR 与实施记录。

## 5. 非目标

- 不在网页中启动 Agent、执行工具或开放任意 workspace；
- 不做自由拖拽式工作流编排器；
- 不引入 React、构建工具、CDN 或后端 Web 框架；
- 不采集完整 prompt/messages 快照；现有 Trace 未记录的内容不伪造；
- 不声称导出文件已完成通用脱敏或可以公开分享；
- 不做自动因果归因、统计显著性排行或新的模型能力评测；
- 不改变模型请求、工具参数、审批决策、压缩策略和任务判定行为。

## 6. 功能需求

| ID | 需求 | 优先级 | 证据类型 |
|---|---|---|---|
| FR-001 | 工具目录必须来自真实 `ToolRegistry`，包含名称、说明、JSON Schema、风险、审批要求及 handler 源码位置。 | Must | 单元测试 / 导出 JSON |
| FR-002 | 架构视图必须展示 Model、Loop、Tools、Approval、Context、Compaction、Trace/Eval 模块及其连接关系；工具支持按风险和名称筛选。 | Must | 浏览器验证 |
| FR-003 | 导出器必须接受一份或多份现有 Eval 报告，保留固定指标、配置、checks、turns 和事件；不得导出报告来源绝对路径或未声明的顶层字段。 | Must | 单元测试 / 真实导出 |
| FR-004 | Loop 视图必须基于事件顺序提供上一步、下一步、播放、暂停、事件选择和详情；显示上下文/prompt Token 曲线及任务 checks。 | Must | 浏览器验证 |
| FR-005 | 对比视图必须支持 A/B 报告选择，突出配置差异，比较成功率、总模型 Token、耗时、步数、压缩/回退和任务 checks。 | Must | 浏览器验证 |
| FR-006 | 新工具调用、结果、参数错误和审批拒绝事件必须携带 `call_id`；导出器必须兼容没有该字段的旧报告。 | Must | 协议测试 / 导出测试 |
| FR-007 | 无数据文件时必须显示可执行的导出说明；有数据时不得要求外部网络资源即可使用三个视图。 | Must | 空数据测试 / 离线浏览器验证 |

| ID | 需求 | 约束 | 证据类型 |

## 9. 指标

本里程碑不追求提高 Agent 成功率，而关注可解释性覆盖：

- 工具目录覆盖率：7/7 内置工具；
- 报告导入：三份 M1.2 基线，18 条任务记录；
- 回放覆盖：模型、工具、压缩、错误与结束事件的已知字段；
- 对比基线：4/6、3/6、3/6 与对应成本，不重新解释为稳定成功率；
- 浏览器外部网络请求：0；
- Live Eval：不适用，除 Trace 增加关联字段外不改变 Agent 行为。

## 10. 安全与边界

Dashboard 是本地只读投影。导出文件可能包含 final response、工具参数和 observation，因此默认被 Git 忽略，并显示“不要公开分享”的提示。字符截断仅控制浏览器载荷，不是脱敏。源码查看由本机静态服务器提供，不调用工具、不读取额外文件、不写入 workspace。

`run_shell` 和 `run_python` 仍不是 Sandbox；本里程碑不增加其执行入口，也不改变审批或隔离能力。

## 11. 风险与未决问题

- 旧报告没有 `call_id`：使用确定性的最佳努力匹配，并在详情中区分 `recorded` 与 `inferred`。
- 旧报告没有代码 revision：显示未记录，不能回填当前 HEAD。
- 完整 observation 可能很长或敏感：限制单字段长度、保留截断标记、数据文件不入库。
- 静态源码链接依赖从仓库根目录启动服务器；文档必须给出唯一推荐命令。
- 自动差异不是因果证明：页面只展示可观察事实。

## 12. 完成条件

- 所有 AC 有确定性测试、真实导出或浏览器证据；
- 全部既有和新增测试通过；
- 无需新增 Live Eval 的理由已记录；
- README、Roadmap、ADR、Tasks 与 Implement 与真实交付一致；
- 原始报告和生成的数据文件保持未跟踪。
