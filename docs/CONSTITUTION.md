# Mini Agent Harness Constitution

状态：Active
版本：1.0.0
生效日期：2026-10-28
适用范围：代码、Prompt、工具、评测、文档和发布流程

本文件定义项目长期遵守的工程原则。它与功能和版本无关；具体变更的行为契约放在该变更的 `spec.md` 中。

## 1. 使命

本项目是一个 **Agent Harness 学习实验室**。目标是通过可运行、可观察、可复现实验，理解模型、Harness、工具、上下文、权限和环境之间的边界。

项目不以“工具数量”“界面完整度”或“像不像 Claude Code”衡量成功。每个阶段至少应增强以下一种理解：

- 模型如何选择和使用工具；
- 工具 observation 如何影响下一步行为；
- 上下文何时失真、膨胀或耗尽；
- Agent 如何验证结果并从错误中恢复；
- 哪些约束由 Prompt 要求，哪些由 Harness 强制执行；
- 更换模型或策略后，行为指标发生了什么变化。

## 2. 原则与约束

### C-01 证据优先于自我描述

**必须**用确定性测试、执行 Trace、固定评测或可检查产物证明 Agent 行为。模型声称“已完成”不能作为完成证据。

行为发生变化时，应该同时记录：

- 预期变化；
- 实际结果；
- 失败案例；
- 尚不能证明的结论。

### C-02 最小充分系统

**必须**优先实现验证当前学习问题所需的最小能力。Web UI、多 Agent、RAG、向量数据库、MCP 和工具市场只有在核心 Harness 稳定且实验证明有必要时才能引入。

新增复杂度必须说明它解决了哪个已观察问题，以及引入了什么新成本。

### C-03 协议正确性优先

工具 Schema、消息角色、`tool_call_id` 配对、最大步数和错误回传属于 Agent 运行契约，**必须**保持正确。

不能因为本地模型“通常能工作”而忽略协议错误。协议错误必须由测试或 Trace 捕获。

### C-04 诚实描述安全边界

**必须**准确区分以下概念：

- Prompt 指令；
- 参数校验；
- 路径 Guardrail；
- 人工审批；
- 进程超时；
- OS 级或容器级 Sandbox。

没有真实隔离时，不得使用“安全 Sandbox”“恶意代码不可逃逸”等表述。高风险工具**必须**默认不可执行，除非用户明确批准；审批不能替代隔离。

### C-05 上下文是被管理的资源

**必须**限制单次 observation 的大小，并优先读取完成任务所需的最小上下文。后续任何上下文压缩都必须通过实验比较成功率、信息损失和成本，而不是只证明压缩函数存在。

### C-06 实验必须可复现

影响 Agent 行为的评测**必须**固定并记录：

- 模型和 Provider；
- 固定任务集；
- 最大步数和关键配置；
- 结果指标；
- 完整 Trace 或可追溯摘要。

确定性测试与 Live Eval 必须分离。单次 Live Eval 只能称为快照，不能称为稳定成功率。

### C-07 规格先于实现

除纯文案修正和极小机械修改外，每个变更**必须**具备：

1. 明确的 `spec.md`；
2. 可执行的 `plan.md`；
3. 可追踪的 `tasks.md`；
4. 包含真实验证证据的 `implement.md`。

研究性 Spike 可以先探索，但在合并前必须把结论回填到上述文档，或明确记录为一次性研究并删除不可合并代码。

v0.2.1 SDD 文档是为了建立流程而进行的一次性 bootstrap 回溯补全，不构成后续可以“先写代码、后补规格”的先例。

### C-08 小步、可逆、可审阅

**必须**选择能验证当前假设的最小改动。不得顺带加入未在规格中声明的功能、架构或依赖。

架构、安全边界和不可逆取舍**应该**通过 ADR 记录。

### C-09 密钥与数据卫生

**不得**提交 `.env`、API Key、私钥或包含敏感信息的 Trace。工具输出和文件内容可能进入 Trace，因此在分享或提交 Trace 前必须检查并脱敏。

测试和评测应优先使用临时目录与合成数据。

### C-10 文档是交付物

文档状态必须与真实实现一致。规格变化时先更新规格；实现偏离计划时在 `implement.md` 记录偏差；能力边界变化时同步 README、路线和 ADR。

## 3. 流程契约

标准流程为：

```text
Constitution
    ↓
Spec
    ↓
Plan
    ↓
Tasks
    ↓
Implement
    ↓
Verify
    ↓
Baseline / Retrospective
```

每个阶段必须在进入下一阶段前通过对应门禁：

- **Spec Gate**：问题、范围、非目标、需求 ID 和验收标准齐全。
- **Plan Gate**：技术方案、文件影响、测试策略、安全边界和回滚方式明确。
- **Tasks Gate**：任务可执行、有依赖顺序、有验收证据要求。
- **Implement Gate**：代码、测试、文档和 Trace 与规格一致。
- **Verification Gate**：确定性测试通过；影响 Agent 行为时完成 Live Eval；已知限制被记录。

## 4. 质量门禁

根据变更类型选择适用门禁，不能跳过与风险直接相关的检查。

| 门禁 | 最低要求 |
|---|---|
| 规格一致性 | 每项验收标准能映射到测试、Trace、评测或人工检查 |
| 协议与单元正确性 | `python3 -m unittest discover -s tests -v` 通过 |
| 静态可运行性 | `python3 -m compileall -q main.py agent providers tools scripts tests` 通过 |
| 格式与补丁卫生 | `git diff --check` 通过；无敏感信息 |
| Agent 行为 | 使用固定任务集运行 Live Eval，并审阅失败样本与工具错误 |
| 安全边界 | 路径、审批和进程能力与文档描述一致；不得夸大隔离能力 |
| 文档 | README、规格、路线、ADR 和基线按影响同步更新 |

纯文档变更不要求重新运行 Live Eval，但必须检查链接、状态、命令和事实是否仍准确。

## 5. 完成定义

一个变更只有在以下条件全部满足时才可标记为 `Verified`：

- 规格中的验收标准全部有证据；
- 必要的测试和静态检查通过；
- 行为变化有 Trace 或评测结果；
- 计划与实现的偏差已经记录；
- 安全边界和使用限制已写入文档；
- 没有未声明的功能扩张；
- 后续工作被明确放入下一阶段，而不是隐藏在“已完成”中。

## 6. 偏差与豁免

如果实现必须偏离规格：

1. 先说明偏离原因和影响；
2. 更新 `spec.md` 或新增 ADR；
3. 在 `implement.md` 记录“计划—实际”差异；
4. 重新检查验收标准。

不得用实现结果反向修改需求措辞来掩盖失败。负面结果和无结论同样必须保留。

## 7. 修订

宪法修订必须：

1. 说明触发修订的真实问题；
2. 评估对现有规格和基线的影响；
3. 更新版本号和日期；
4. 必要时新增 ADR；
5. 在实施文档中记录迁移结果。

原则文本应稳定。若某个规则只适用于一次变更，应写入该变更的规格，而不是修改宪法。
